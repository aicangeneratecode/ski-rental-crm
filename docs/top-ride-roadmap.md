# TOP RIDE — этапный план развития

Утверждено 5 ноября 2026 года.

## Исключения по решению владельца
Не реализуем в этой дорожной карте:
- разграничение прав сотрудников;
- отдельный учёт залогов;
- частичный возврат внутри одной аренды.

Текущая модель единой авторизованной сессии остаётся без изменений. Не объявляйте её ролевой моделью.

- [x] Сохранить платежи и аудит для архивных броней, добавить события ARCHIVED и RESTORED.
- [x] Исключить архивные брони из оперативных задач и календаря, оставить отдельный фильтр «Архив».

- [ ] Проверить весь сценарий в браузере на тестовом аккаунте и рабочую БД командой db:doctor.

## Этап 2. Работа с бронированием
- [x] Редактирование даты, клиента, оборудования, скидки и примечаний до выдачи с серверной проверкой конфликтов.
- [x] Продление забронированной или выданной аренды с пересчётом суммы и проверкой будущих броней.
- [x] Замена инвентаря и изменение даты до выдачи; после выдачи состав и дата начала блокируются.
- [x] Досрочная выдача максимум на один день с обязательной причиной, проверкой свободного оборудования и записью в истории.
- [x] Интеграционные PostgreSQL-тесты сохранения оплат, пересчёта стоимости, конфликтов, продления и защиты от переплаты.
- [x] Шаблоны комплектов (лыжи/сноуборд + ботинки + шлем или палки) с ручным выбором правильного размера.

Перед использованием в рабочем прокате остаётся браузерная проверка на тестовых данных и резервная копия перед миграцией `20261105171000_booking_edits`.

## Этап 3. Инвентарь и клиенты
- [x] Автоматическая запись выдачи и возврата, блокировка до осмотра, журнал осмотра/обслуживания/повреждений.
- [x] QR-коды удалены из системы по решению владельца.
- [x] Повторное бронирование из карточки клиента с предзаполнением клиента и доступных предметов; даты и скидка новые.
- [x] Объединение дублирующихся клиентов с подтверждением: аренды и платежи сохранены, исходная карточка остаётся скрытым псевдонимом.

Для применения этапа 3 нужна миграция `20261105175000_equipment_maintenance_customer_merges`, резервная копия БД и локальная проверка полного рабочего цикла.

## Этап 4. Календарь и удобство
- [x] Мобильный календарь: компактная сетка месяца/недели, список аренд на выбранный день, отдельный однодневный список занятости оборудования.
- [x] Создание новой брони из календаря на выбранную дату: форма открывается с предзаполненным началом и концом.
- [x] Перенос забронированной аренды: drag-and-drop в календаре на ПК или кнопка «Перенести» на телефоне; подтверждение, сохранение длительности, транзакционная проверка конфликтов и оплат.
- [x] Группировка одинаковой модели, размера, тарифа и цены; кнопка добавления автоматически назначает конкретный свободный экземпляр с финальной проверкой на сервере.

### Изменения по решению владельца
- [x] QR-коды и все маршруты их печати удалены из системы.
- [x] Архивные завершённые/отменённые брони можно удалить окончательно через корзину с подтверждением. При этом удаляются связанные платежи и журнал действий аренды; состояние обслуживания снаряжения сохраняется. Действие не отменяется.

Этап 4 не требует новой миграции. Но при обновлении с более старых веток
должны быть применены миграции этапов 1–3 после резервного копирования БД.

## Работа с БД после первого этапа

Новая миграция: `prisma/migrations/20261105160000_booking_archive`.

Перед её применением к рабочей БД создайте резервную копию и проверьте `DATABASE_URL`.
Далее `npm run db:setup` применяет новую колонку `Booking.archivedAt` и типы событий.
Не используйте `prisma migrate reset` на существующей базе.

Изменения в коде и зеленая CI-проверка не гарантируют, что локальная БД пользователя уже обновлена.
